\chapter{Diseño del sistema}
Este capítulo define qué debe hacer el sistema y cómo se estructura. Presenta el diseño conceptual, los requerimientos de software, el diseño modular y el diseño detallado: instrumento de captura, modelo de afinidad, flujos, contratos de comunicación, base de datos, arquitectura de software y arquitectura de nube. La construcción de estos elementos se describe en el capítulo siguiente.

\section{Diseño conceptual}
El aspirante responde un cuestionario en el sitio web. La API publica sus respuestas en un bus de eventos y los demás servicios las procesan en cadena: el extractor mide qué tan bien sus respuestas coinciden con los criterios de cada carrera, el clasificador estima la afinidad con cada carrera del área elegida y el constructor de respuesta entrega las tres carreras con mayor coincidencia junto con las escuelas donde se imparten (figura~\ref{fig:diseno-conceptual}).

\section{Diseño modular}
El sistema se divide en servicios desacoplados con una responsabilidad cada uno (figura~\ref{fig:diseno-modular}). Esto permite que captura, análisis de texto, predicción y persistencia escalen y fallen de forma independiente.

\begin{figure}[H]
\centering
\includegraphics[angle=90,height=0.82\textheight,width=\textwidth,keepaspectratio]{imagenes/modular.png}
\caption{Diseño modular del sistema}
\label{fig:diseno-modular}
\end{figure}

\begin{itemize}
    \item \textbf{Sitio web:} interfaz en Vue.js y Nuxt. Guía al aspirante por el cuestionario y muestra los resultados.
    \item \textbf{API:} servicio en FastAPI. Valida las solicitudes con esquemas Pydantic, consulta la base de datos y publica el evento inicial.
    \item \textbf{Orquestador (Redis):} bus de eventos entre servicios. Cada servicio lee de su propio flujo y publica en el del siguiente.
    \item \textbf{Extractor:} servicio que consulta el modelo de decisiones Jev para medir la coincidencia entre las respuestas del aspirante y los criterios de las carreras.
    \item \textbf{Clasificador:} servicio que aloja un modelo Random Forest por área y estima la afinidad del aspirante con cada carrera.
    \item \textbf{Constructor de respuesta:} servicio que ordena las afinidades, aplica el umbral mínimo, selecciona las tres mejores carreras y agrega sus escuelas.
    \item \textbf{Base de datos Athena:} PostgreSQL con la oferta académica, los criterios, las respuestas procesadas y los resultados.
\end{itemize}

\section{Diseño detallado}

\subsection{Instrumento de captura}
El cuestionario sustituye las 100 afirmaciones cerradas del instrumento institucional por dos bloques que se complementan. Ambos se ajustan al área elegida y se alimentan de los documentos oficiales de cada carrera.

\noindent\textbf{1. Valoración de objetivos.}\par\smallskip
Cada carrera aporta una pregunta derivada de su objetivo formativo. El aspirante la califica de 1 a 5 y, si lo desea, justifica su respuesta. Con 5 la justificación es obligatoria. Las preguntas se muestran en bloques de seis para limitar la carga cognitiva. El área 1 tiene 43 preguntas, el área 2 tiene 12 y el área 3 tiene 11.

\noindent\textbf{2. Cuestionario RIASEC.}\par\smallskip
Se presenta una pregunta por dimensión RIASEC. Cada una ofrece una lista de habilidades, con el resumen del criterio de cada carrera del área, y una pregunta abierta. El aspirante marca las habilidades en las que se reconoce y describe en texto libre su experiencia con ellas. Las habilidades marcadas se tratan como prioritarias. El texto abierto sirve para verificar que la habilidad declarada tenga respaldo y para detectar coincidencias con criterios que el aspirante no marcó.

\subsection{Modelado de criterios con el modelo RIASEC}
El modelo de Holland~\cite{Holland1997} agrupa intereses y actividades en seis dimensiones: Realista ($R$), Investigador ($I$), Artístico ($A$), Social ($S$), Emprendedor ($E$) y Convencional ($C$). Aquí se usa como esquema para organizar los criterios de cada carrera, no como diagnóstico de personalidad.

Cada carrera tiene un criterio principal, que resume su habilidad central, y un criterio de perfil por dimensión. Los criterios se extraen de los documentos oficiales y se clasifican por dimensión con las reglas definidas por la asesora en psicología, Lic. Paola Alejandra Luna Cabrera (anexo~\ref{anexo:extraccion}). La dimensión $A$ casi no aparece en los documentos y solo se registró en una carrera del área 2. Por esa razón el modelo de afinidad usa las dimensiones $R$, $I$, $S$, $E$ y $C$.

\subsection{Modelo de afinidad}
Para cada área se entrena un modelo Random Forest~\cite{Breiman2001}. El modelo no asigna una clase por aspirante: estima un índice de afinidad entre 0 y 1 para cada par aspirante-carrera. Este diseño permite ordenar todas las carreras del área y entregar las tres mejores con su porcentaje, algo que una etiqueta única no ofrece. Por esto la tarea se formula como regresión de la afinidad y la clasificación de carreras resulta de ordenar los índices.

Cada fila de entrada corresponde a una carrera evaluada para un aspirante y contiene las variables de la tabla~\ref{tab:features}, además de una codificación \textit{one-hot} de la carrera. El número de columnas depende del área: 55 en el área 1 (43 carreras y 12 variables), 24 en el área 2 y 23 en el área 3.

\subsection{Datos de entrenamiento}
No existen registros históricos que relacionen las respuestas de aspirantes con la carrera que les convino. Por ello el modelo se entrena con aspirantes sintéticos, generados a partir de los criterios de cada carrera, y con una etiqueta calculada mediante una fórmula determinista. Con $\bar{a}_k$ el ajuste por repetición de la dimensión $k$:
\begin{equation}
\bar{a}_k =
\begin{cases}
0 & r_k = 0 \\
m_k + 0.15\,(1-m_k)\left(1-e^{-(r_k-1)/2}\right) & r_k \ge 1
\end{cases}
\end{equation}
\begin{equation}
S = \frac{1}{5}\sum_{k}\bar{a}_k, \qquad
B = 0.25\,O + 0.30\,P + 0.45\,S
\end{equation}
\begin{equation}
H = \frac{0.30\,P + 0.45\,S}{0.75}, \qquad
y = B\,\bigl(1 - 0.20\,\lvert O - H\rvert\bigr)
\end{equation}
La fórmula pondera más la evidencia de habilidades ($S$) que la calificación declarada ($O$) y penaliza al aspirante cuya calificación no concuerda con la evidencia ($\lvert O - H\rvert$). Los pesos son una decisión de diseño. No provienen de un estudio empírico y deben ajustarse con datos reales.

Los aspirantes sintéticos se reparten en ocho escenarios que cubren desde perfiles con evidencia completa hasta perfiles sin coincidencias, y se complementan con perfiles dirigidos para cubrir todo el rango de $y$ en cada carrera. La partición es 70\,\% para entrenamiento, 15\,\% para validación y 15\,\% para prueba, estratificada por escenario. Cada aspirante pertenece a una sola partición y cada uno es independiente de los demás, por lo que no hay fuga de datos entre particiones.

\subsection{Diagramas de flujo modulares}
El procesamiento es reactivo: cada servicio recibe un evento, lo procesa y publica el siguiente.

\noindent\textbf{1. Sitio web.}\par\smallskip
El aspirante pasa por cinco pantallas: introducción; datos, área y términos; objetivos; RIASEC; y resultados (figura~\ref{fig:flujo-website}). Tras elegir el área, el sitio solicita a la API las preguntas correspondientes. Al terminar el cuestionario, valida los campos y envía las respuestas en un solo objeto JSON. Después espera el resultado para mostrar las tres carreras y sus escuelas.

\caption{Diagrama de flujo del sitio web}
\label{fig:flujo-website}

\noindent\textbf{2. API.}\par\smallskip
La API expone cuatro operaciones: lista de áreas, preguntas de un área, recepción de respuestas y consulta de resultados (figura~\ref{fig:flujo-api}). Al recibir las respuestas, valida su estructura con Pydantic, genera un identificador único (UUID), registra al usuario y publica un \texttt{ExtractorEvent}. Responde de inmediato con el UUID, que el sitio usa para consultar el resultado cuando esté listo.

\noindent\textbf{3. Extractor.}\par\smallskip
El extractor lee el \texttt{ExtractorEvent}, arma un prompt con las respuestas del aspirante y los criterios de las carreras del área y consulta a Jev en una sola llamada (figura~\ref{fig:flujo-extractor}). Con la respuesta construye la lista de habilidades con su porcentaje de coincidencia y publica un \texttt{ClassifierEvent}.

\noindent\textbf{4. Clasificador y constructor de respuesta.}\par\smallskip
El clasificador lee el \texttt{ClassifierEvent}, arma el vector de características, aplica el modelo del área elegida y publica un \texttt{ConstructorEvent} con la afinidad de cada carrera. El constructor ordena las carreras de mayor a menor y verifica que la mejor supere el 50\,\% de coincidencia. Si la supera, toma las tres primeras, agrega sus escuelas y guarda el resultado. Si no la supera, guarda el estado de clasificación fallida (figura~\ref{fig:flujo-classifier}). En ambos casos publica un \texttt{ResponseEvent} para notificar a la API.

\subsection{Diagrama entidad-relación}
La información se almacena en una base de datos relacional llamada Athena, en PostgreSQL, con 13 tablas (figura~\ref{fig:arquitectura-base-datos}). Se organizan en cuatro grupos:
\begin{enumerate}
    \item \textbf{Oferta académica:} \texttt{areas}, \texttt{carreras}, \texttt{escuelas} y \texttt{escuela\_carrera}. La tabla \texttt{carreras} guarda el objetivo formativo y la pregunta de objetivo de cada programa. \texttt{escuela\_carrera} relaciona carreras con escuelas, porque una carrera se imparte en varios planteles.
    \item \textbf{Criterios:} \texttt{tipos\_riasec}, \texttt{tipos\_criterio} y \texttt{criterios}. Cada criterio pertenece a una carrera, a una dimensión RIASEC y a un tipo (principal o de perfil), y guarda su descripción y un resumen de hasta 100 caracteres.
    \item \textbf{Cuestionario:} \texttt{pregunta\_cuestionario} y \texttt{cuestionarios}. La primera guarda el texto de las preguntas por dimensión y la segunda las asigna a cada área.
    \item \textbf{Operación:} \texttt{usuarios}, \texttt{puntaje\_objetivo}, \texttt{usuario\_criterio} y \texttt{resultados}. \texttt{usuarios} identifica cada sesión con un UUID, un estatus de procesamiento (pendiente, extraído, clasificado o completado) y un tipo (entrenamiento, validación, prueba o real). Las otras tres tablas guardan la calificación de cada objetivo, la coincidencia y repeticiones de cada criterio, y el porcentaje de coincidencia por carrera.
\end{enumerate}

\subsection{Arquitectura de software}
La arquitectura es de microservicios desacoplados que se comunican por eventos a través de Redis (figura~\ref{fig:arquitectura-software}). Las tareas pesadas, como consultar a Jev o aplicar el modelo, no bloquean a la API, que responde al sitio en cuanto registra la solicitud. Redis se usa mediante flujos (\textit{streams}) con grupos de consumo~\cite{RedisStreams}, de modo que cada evento se entrega a un solo consumidor del servicio.

\subsection{Arquitectura de nube}
El despliegue objetivo corre en Google Cloud dentro de una red privada virtual (VPC), como se muestra en la figura~\ref{fig:arquitectura-nube}. Los servicios se ejecutan como contenedores en Google Kubernetes Engine. La base de datos se aloja en Cloud SQL para PostgreSQL y el orquestador en Memorystore para Redis. Solo el sitio web y la API son accesibles desde internet, a través de un balanceador HTTPS. La comunicación interna usa direcciones privadas.
