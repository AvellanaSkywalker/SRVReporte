\section{Comparativa tecnológica}
En esta sección se fundamenta la selección de las herramientas, lenguajes, algoritmos y plataformas que integran la solución propuesta. La arquitectura del sistema demanda el desacoplamiento de servicios, el procesamiento concurrente de solicitudes, la extracción de características textuales y la ejecución de modelos de aprendizaje automático supervisado. Para asegurar la robustez, mantenibilidad y escalabilidad del proyecto, se realizó una evaluación sistemática de alternativas tecnológicas en los componentes críticos de la arquitectura.

\subsection{Lenguajes de programación y frameworks de backend}
El desarrollo del backend requiere un entorno capaz de orquestar la lógica de negocio, comunicarse de forma asíncrona mediante eventos y ejecutar inferencias sobre modelos de aprendizaje automático. Se compararon tres alternativas principales: Python con FastAPI, Node.js con Express, y Java con Spring Boot.

Python se seleccionó como lenguaje principal debido a su posición estándar en ciencia de datos y aprendizaje automático, lo que permite integrar directamente bibliotecas como Scikit-Learn, NumPy y Pandas sin necesidad de puentes entre lenguajes. Dentro del ecosistema Python, FastAPI ofrece ventajas sustanciales frente a frameworks tradicionales como Flask o Django: está construido sobre estándares abiertos (ASGI, Starlette y Pydantic), proporciona soporte nativo para programación asíncrona (\texttt{async/await}), realiza validación automática y estricta de esquemas de datos con tipado estático, y genera documentación interactiva OpenAPI de forma nativa. \subsection{Algoritmos de aprendizaje supervisado}
El núcleo predictivo estima qué tan afín es el aspirante a cada programa del área elegida. Se compararon cuatro algoritmos supervisados: Random Forest, Perceptrón Multicapa (MLP), Máquinas de Vectores de Soporte (SVM) y Regresión Logística.

Se seleccionó Random Forest por tres razones. Primero, el ensamble de árboles por agregación (\textit{bagging}) reduce el sobreajuste. Segundo, funciona bien con datos tabulares que mezclan variables continuas y binarias, como las del modelo. Tercero, permite calcular la importancia de las variables, lo que facilita explicar el resultado. Las redes neuronales requieren más datos y un ajuste más delicado de hiperparámetros; Random Forest se comporta de forma estable con pocos hiperparámetros y sin GPU. Además, la salida requerida es un índice continuo de afinidad por carrera, que Random Forest produce de forma nativa en su versión de regresión. \subsection{Mecanismos de orquestación y mensajería orientada a eventos}
El flujo operativo entre la interfaz web, el extractor de habilidades por PLN y el clasificador supervisado se diseñó bajo un patrón orientado a eventos para evitar bloqueos por operaciones síncronas de cómputo intensivo. Se evaluaron Redis, RabbitMQ y Apache Kafka.

Se seleccionó Redis como bus de eventos. Al almacenar en memoria, ofrece latencias submilisegundo, y sus flujos con grupos de consumo~\cite{RedisStreams} bastan para repartir eventos entre servicios. Kafka está orientado a grandes volúmenes de eventos distribuidos y exige operar un clúster. RabbitMQ añade configuración de enrutamiento que este sistema no necesita. Redis tiene una huella de memoria pequeña y es sencillo de ejecutar en contenedores. Su limitación es la durabilidad: con la confirmación al leer, un evento que falla durante su procesamiento no se reentrega. La tabla~\ref{tab:comp-mensajeria} expone la comparación.

\subsection{Infraestructura de despliegue, contenerización e integración continua}
Para garantizar la reproducibilidad y el despliegue confiable de los microservicios, se requería una infraestructura desacoplada, estandarizada y automatizada. Se evaluó la combinación de Docker, Google Cloud Platform (GCP) y GitHub Actions frente a esquemas tradicionales en servidores locales y frente a proveedores alternativos como Amazon Web Services (AWS).

Docker empaqueta cada servicio con sus dependencias, de modo que el entorno de desarrollo sea el mismo que el de despliegue. Se eligió Google Cloud por su integración con Kubernetes (Google Kubernetes Engine), su base de datos administrada (Cloud SQL) y su registro de imágenes (Artifact Registry). GitHub Actions automatiza el flujo de CI/CD desde el mismo repositorio donde se aloja el código. En desarrollo se usó un clúster K3s local con un \textit{runner} propio de GitHub Actions, que evita el costo de un clúster en la nube durante las pruebas. \subsection{Evaluación de coincidencias en texto libre}
El extractor debe medir qué tan bien una respuesta abierta respalda cada criterio de las carreras. Un aspirante del área 1 puede generar más de 200 comparaciones en una sola evaluación. Se compararon cuatro enfoques: un modelo de decisiones tipadas (Jev), un modelo de lenguaje generativo, representaciones semánticas de oraciones~\cite{Reimers2019SBERT} y TF-IDF con similitud coseno.

Se seleccionó Jev porque devuelve valores tipados (puntuación, opción o sí/no) en lugar de texto, por lo que no requiere analizar la respuesta, y contesta todas las preguntas en una sola llamada~\cite{JevAPI2026}. Eso mantiene el costo en menos de 0.003 USD por evaluación (capítulo de pruebas). Sus desventajas son la dependencia de un servicio externo y el límite de 64,000 tokens por solicitud.
